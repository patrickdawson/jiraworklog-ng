# Tauri migration: plan and state

Branch `tauri-rewrite` (not pushed). Last updated 2026-11-11, after milestone 11
(cut-over): the repository holds only the Tauri app, now at version
0.10.0-beta.2 (0.9.0 at the cut-over; beta.1 was the first test install).

## Goal

Replace Electron + embedded Next.js server with Tauri 2: a Rust backend and a
React SPA in WebView2. The goals are a smaller download, less RAM and a faster
start. The Electron app (0.8.0, still on `main` until this branch is
merged, and in the history before `10434ed`) was the reference
implementation until the cut-over in milestone 11. Comments of the form
"Port of src/…" or "electron/main.ts" in the Rust and UI code name files of
that app.

| | Electron 0.8.0 | Tauri (skeleton, milestone 1) | Tauri (milestone 7) | Tauri (milestone 10, size pass) |
|---|---|---|---|---|
| Installer | ~96 MB | 1.9 MB | 4.2 MB (4,381,235 B) | 2.9 MB (2,878,426 B) |
| Installed | 328 MB | ~9 MB exe | 17.1 MB exe (17,084,416 B) | 7.5 MB exe (7,492,608 B) |

The PDF engine (milestone 7) adds 0.6 MB to the exe: a plain
`cargo build --release -p jiraworklog` gives 16,335,360 B at milestone 6
(4bde1f0) and 16,958,464 B now (+623,104 B, fonts included). Most of the
growth since milestone 1 came earlier (SQLite, ureq + native-tls, tray,
plugins). The size pass of milestone 10 (`opt-level = "s"`, LTO, one
codegen unit, `panic = "abort"`) brought the exe to 7.5 MB, below the
8–15 MB expectation; see "Size pass".

## Decisions

- **Everything except the views is Rust:** SQLite, migrations, all server
  actions, the domain logic, the Jira client, PDF, tray, menu and away
  detection.
- **UI:** Vite + React 19 + Tailwind 4 SPA. The components come over from
  `src/components/` nearly unchanged (see "How the UI port works").
- **E2E:** the 15 Playwright specs are ported to WebdriverIO + `tauri-driver`
  (`e2e/`, milestone 9), plus Rust unit tests.
- **Desktop only:** browser mode ("Läuft im Browser" in the README) goes away.
- **Same data folder:** `%APPDATA%\jiraworklog-ng\jiraworklog.db`, named after
  package.json `name`. `%APPDATA%\JiraWorklog` is a stale copy from July; do
  not use it.
- **Jira credentials stay in the `settings` table** so the old and new app stay
  compatible. Moving them to the Windows Credential Manager (`keyring`) is
  optional, after the Electron app is retired.
- **PDF: hand-made layout on `pdf-writer`, not typst** (milestone 7). Both
  reports are two plain tables; typst as a library would bring its whole
  layout engine, `typst-library` (citations, syntax highlighting, image
  decoders) and a `World` impl for two layouts. `pdf-writer` + `subsetter`
  (no default features) + `ttf-parser` + `miniz_oxide` cost about 0.6 MB of
  exe including the fonts (see the size table). Fonts: Arimo Regular/Bold,
  SIL OFL 1.1, metric-compatible with the Helvetica the old react-pdf PDFs
  used, pre-subset with fontTools to Latin, Greek, Cyrillic and common
  symbols (~95 KB each, `crates/core/assets/fonts/`, license in `OFL.txt`)
  and subset again per document.

### src-tauri

- `commands.rs`: settings, `buchen_data`, `kalender_data`, `auswertung_data`,
  `group_entries`, timer, entries, group colors, away,
  `show_window`, auto-launch, Jira (`preview_*`, `submit_*`,
  `test_jira_connection`), `get/set_force_booking`, `cleanup_old_entries`,
  `export_worklog_pdf(range, anchor)`, `export_category_pdf(anchor)`. The
  export commands render in Rust, release the DB lock, then open the native
  "Speichern unter" (dialog plugin, parent = main window, starting in
  Downloads, file name filled in) and write the file; they return the path or
  `null` on cancel. The Electron app had no `will-download` handler, so its
  download also ended in Electron's default save dialog in Downloads.
  Errors reach the UI as strings (`CommandError`). Submit and connection
  test are async + `spawn_blocking`; the DB mutex is held only to plan and to
  mark each sent worklog, never during HTTP.
- `events.rs`: `TimerStopped`, `AwayEnded`, `Navigate` (typed via tauri-specta).
- `tray.rs`, `menu.rs`, `window.rs`: tray, app menu, close-to-tray.
- `power.rs`: hidden top-level window (class `JiraWorklogPowerWatcher`) for WTS
  lock/unlock and `WM_POWERBROADCAST`. It is not message-only, because those
  windows get no broadcasts.
- `state.rs`: `Db` (mutex), `ForceBooking` (in memory only), `Zoom`, data paths.
- Plugins: single-instance, log (`tauri-main.log` next to the DB, local time),
  autostart (Run key `JiraWorklog`), dialog, opener.
- `build.rs` embeds a Common-Controls v6 manifest into every binary.
  Without it, the test harness aborts with `STATUS_ENTRYPOINT_NOT_FOUND`.
- `upgrade.rs` (milestone 10): `jiraworklog.exe --post-install
  [--from-electron]`, handled in `main()` before Tauri starts; real
  registry via `windows-registry`; log `upgrade.log` next to the DB. Only
  the installer passes the flag: never run it by hand here (it rewrites the
  Run key).
- `lib.rs` installs a panic hook that logs "panic: …" to `tauri-main.log`
  (release builds abort on panic).
- `e2e.rs`, cargo feature `e2e` (milestone 9), built only by `npm run
  tauri:e2e` into `target/e2e`: no single-instance lock, and an init script
  with a fake UI clock (`Date` + `window.__jwlE2eClockOffsetMs`). Normal
  debug/release builds do not contain it.

### E2E suite (`e2e/`, milestone 9)

Run: `npm --prefix e2e ci` once, then `npm run tauri:e2e` (Node 24).
`JWL_E2E_SKIP_BUILD=1` reuses the last exe; one spec:
`npm run tauri:e2e -- --spec specs/kalender.e2e.ts`.

- `wdio.conf.ts` `onPrepare`: finds/fetches the drivers, builds
  `npx tauri build --debug --no-bundle --features e2e` with
  `CARGO_TARGET_DIR=target/e2e` (debug exe with the bundled UI, origin
  `http://tauri.localhost`; a plain `cargo build` would load the Vite dev
  URL), wipes `target/e2e/run`, starts the Jira mock on 127.0.0.1:4570 and
  `tauri-driver --port 4444 --native-driver <msedgedriver>` with
  `JWL_DB_PATH=target/e2e/run/jiraworklog.db`. The app creates and migrates
  that DB itself; its log lands next to it. `onComplete` stops tauri-driver
  by PID (`taskkill /T`) and sweeps leftovers by full exe path.
- One WebDriver session (= one app launch) per spec file; `maxInstances: 1`.
- Drivers (`support/tools.ts`): tauri-driver 2.1.0 via `cargo install
  --registry crates-io --root target/tools` (`target/tools/bin`);
  msedgedriver for the newest WebView2 runtime found under
  `C:\Program Files (x86)\Microsoft\EdgeWebView\Application`, downloaded from
  `https://msedgedriver.microsoft.com/<version>/edgedriver_win64.zip` into
  `target/tools/msedgedriver/<version>/`. Overrides: `JWL_TAURI_DRIVER`,
  `JWL_MSEDGEDRIVER`, `JWL_WEBVIEW2_VERSION`. Used here: tauri-driver 2.1.0,
  WebView2 157.0.4341.46 with msedgedriver 157.0.4341.46 (the runtime
  updated itself from .42 during the milestone; the next run fetched the new
  driver by itself).
- `support/db.ts`: `resetDb`, `seedSettings`, `seedEntries`,
  `getSettingsRow`, `getEntries`, `getGroupColorRows` with the old baseline,
  plain SQL on better-sqlite3 (a dependency of `e2e/`, not of the root).
- `support/page.ts`: Playwright-style locators over WebdriverIO
  (`getByRole/Text/Label/Placeholder/Title/TestId`, `filter({ hasText })`,
  `nth/first/last`), resolved in the page in one round trip; actions are
  strict and real WebDriver input; assertions poll for 10 s
  (`toBeVisible`, `toHaveCount`, `toHaveText`, `toContainText`,
  `toHaveValue`, `toHaveAttribute`, `toHaveCSS`, `toBeChecked`,
  `toBeFocused`, `toBeInViewport`, `toHaveURL`, `expect.poll`).
  `page.goto(route)` loads `http://tauri.localhost/?nav=<n>#<route>` (the
  changing query forces a full load, as `page.goto` did). Also
  `page.emitEvent`, `page.fastForward`, `page.wheel`, `page.setViewportSize`
  and `page.consoleErrorsSince` (reads ERROR lines from the app log, where
  `ui/src/lib/log.ts` forwards `console.error`, `error` and
  `unhandledrejection`).
- WebView2 logs "IPC custom protocol failed, Tauri will now use the
  postMessage interface" as a warning under msedgedriver; harmless, IPC works.

#### How the UI port works

Copy the component from `src/components/` and change as little as possible:

> After the port the shims below were removed: components import `Link`,
> `useNavigate` and `useLocation` from react-router, `router.refresh()` is
> `reloadAll()` from `ui/src/lib/query.ts`, `ui/src/db/schema.ts` is
> `ui/src/lib/categories.ts`, and the version is `__APP_VERSION__`.

- `next/link` and `next/navigation` are aliased (vite.config.ts, tsconfig
  paths) to shims in `ui/src/next/` on top of react-router.
  `router.refresh()` = invalidate all queries.
- `ui/src/lib/actions.ts` keeps the old server-action names and signatures but
  calls Tauri commands, then invalidates all queries (= `revalidatePath`).

### Upgrade design

Tauri's NSIS template (read in `target/release/nsis/x64/installer.nsi`) with
`installerHooks: "windows/installer-hooks.nsh"`:

1. `Section Install` → **`NSIS_HOOK_PREINSTALL`** (before any file is copied):
   - Electron install = `Uninstall JiraWorklog.exe` in `InstallLocation` of
     `HKCU\Software\3783ec4d-…` (fallback: the default folder).
   - Stop it by **full path**: `CheckIfAppIsRunning` (Tauri's own macro,
     Restart Manager on `…\jiraworklog-ng\JiraWorklog.exe`). GUI: asks
     "close it?" (cancel aborts the install); silent/passive: closes it.
     The Electron app writes its DB through SQLite (WAL), so a forced stop
     loses nothing committed.
   - `ExecWait '"…\Uninstall JiraWorklog.exe" /currentuser /S _?=<dir>'`
     (in place, so ExecWait really waits), then delete the uninstaller and
     `RMDir` the folder (not recursive). Exit code ≠ 0 or `JiraWorklog.exe`
     still there → German message box (`/SD IDOK`) and `Abort`: never two
     apps side by side.
   - Must run before Tauri's shortcuts: both apps call them
     `JiraWorklog.lnk` in the same places, and the old uninstaller deletes
     those names.
2. Tauri's `CheckIfAppIsRunning` for `$INSTDIR\jiraworklog.exe` (also by
   path), files, uninstall key `HKCU\...\Uninstall\JiraWorklog`,
   `HKCU\Software\JiraWorklog\JiraWorklog` (= install dir, named after
   `bundle.publisher`: keep the publisher stable), Start menu shortcut
   `$SMPROGRAMS\JiraWorklog.lnk` (same place as Electron's), desktop
   shortcut (silent/passive: always; GUI: the finish page's "create desktop
   shortcut" box, checked by default). Both get the AppUserModelId
   `com.jiraworklog.ng`, the same as Electron's appId.
3. **`NSIS_HOOK_POSTINSTALL`**, on every install: `ExecWait
   '"$INSTDIR\jiraworklog.exe" --post-install'`, plus ` --from-electron`
   if step 1 removed the Electron app. `main()` handles the flag before
   Tauri starts (no window, no single-instance lock, no tray) →
   `src-tauri/src/upgrade.rs` → `jwl_core::electron_upgrade`:
   - only with `--from-electron`: `db::backup_existing(db, "electron")` →
     `jiraworklog.db.backup-electron-<UTC stamp>` (VACUUM INTO, WAL
     included, no migration). The first app start still makes its own
     `backup-<stamp>` if a schema migration is pending (none is today: both
     apps are at 0008).
   - `migrate_autostart(reg, current_exe)`:
     - `electron.app.JiraWorklog` present and not disabled in
       `StartupApproved\Run` → write `JiraWorklog` = `<exe path> ` (the
       plugin's format, see below) plus `02 00…00` in `StartupApproved\Run`
       if that key exists (as auto-launch does); then delete the old Run and
       StartupApproved values (`Carried`). Disabled in Task Manager → old
       values deleted, nothing set (`WasDisabled`). This also catches a Run
       value an Electron app removed by hand left behind.
     - no Electron value: an existing `JiraWorklog` value that points
       elsewhere is rewritten to this exe (`Repointed`, e.g. another install
       folder), one that already matches is left (`Kept`), none → nothing
       (`NotSet`). Task Manager's state of `JiraWorklog` is never changed.
   - Value format, from the sources in the cargo registry:
     `tauri-plugin-autostart` 2.7.0 builds `auto-launch` 0.6.0 with
     `app_name = package_info().name` (= `productName` `JiraWorklog`),
     `app_path = current_exe().display()`, no args (`init(…, None)`);
     `auto-launch` writes `format!("{} {}", app_path, args.join(" "))` →
     unquoted path plus one trailing space. Its `is_enabled` only checks
     that the Run value exists and is not disabled in StartupApproved, so
     Einstellungen → Desktop shows "on" after the upgrade.
   - Appends what it did to `%APPDATA%\jiraworklog-ng\upgrade.log`; exit
     code ≠ 0 only adds a `DetailPrint` (the install stays). Registry access
     is `windows-registry` 0.6 (the crate auto-launch uses) behind the
     `StartupRegistry` trait; all tests use `FakeStartupRegistry`.
4. **Uninstall hooks.** Tauri's template deletes the Run value
   `JiraWorklog` whenever the uninstaller runs without `/UPDATE`.
   - `NSIS_HOOK_PREUNINSTALL`: if the uninstaller runs in place
     (`$EXEDIR == $INSTDIR`, i.e. our installer started it with `_?=` for
     "uninstall first"; from Settings → Apps or by double-click NSIS runs a
     copy in `%TEMP%`), remember the Run value.

- `strip` changes nothing on MSVC (symbols live in the PDB anyway); it is
  kept for clarity. LTO alone makes the installer *larger* (the exe
  compresses worse).
- `panic = "abort"` is the biggest single step (~4 MB of unwind tables and
  landing pads). Behaviour change: main-thread code (sync commands, menu,
  tray events, window events) already ended the app on a panic, because
  tao catches it in the event loop and resumes it afterwards. Only the
  async commands (Jira submit/test, PDF export) and the tray / power
  threads used to survive a panic; now the app ends. SQLite keeps the data
  consistent either way (every write is one transaction; a Jira worklog is
  marked right after it was sent). `run` installs a panic hook that writes
  "panic: …" to `tauri-main.log` and flushes it first.
- `"s"` over `"z"` for speed: the heaviest work on the real-DB copy
  (`export_pdfs … all month:2026-10-01` / `dump_pages … auswertung all`,
  incl. process start, 3 runs each) took ~410 / ~330 ms at opt 3, ~455 /
  ~380 ms at `"s"`, ~555 / ~425 ms at `"z"`.
- `cargo bloat` was not run: installing it into `target/tools` was blocked
  by the session's permission rules. Not needed for the decision above.

## Rules learned the hard way

- **Never target processes by name.** The installed Electron app runs as
  `JiraWorklog.exe`, and Windows process names match case-insensitively. A
  `Get-Process jiraworklog | Stop-Process` killed the live app once. Match the
  full path (`C:\dev\jiraworklog-ng\target\debug\jiraworklog.exe`), and find
  Vite by its command line.
- **Never write to the live DB.** Work on `data/real-copy/`; open the live DB
  read-only at most.
- **`tauri dev` restarts the app on every Rust change**, including
  `cargo fmt`. In-memory state such as a simulated lock is lost.
- `cargo search` needs `--registry crates-io`; crates come from the
  corporate kellnr mirror.
- A `location.hash = ...` set by a CDP script right after a router
  navigation can be lost; click the app's own links instead.
- **Never drive a native file dialog by a loose UI Automation lookup.** In
  milestone 7 a test script searched the "Speichern unter" dialog for
  AutomationId `1`, which matched a file in the list (Downloads) instead of
  the Save button; with the overwrite prompt confirmed, it replaced the
  user's `Downloadsxapta-bericht-2026-11.pdf` (made on 2 Nov by the old
  app). Native dialogs also pop up on the user's screen while they work.
  If a save must be automated: take the window handles (file name `Edit`
  under `FileNameControlHost`, `Button` id 1 "Speichern" as a direct child),
  set a full path inside the scratchpad, read it back, refuse anything
  else. Prefer verifying the write path without the dialog.
- New drizzle-style migrations need `when` > 1779340767574 and an entry in
  `crates/core/src/migrations.rs`.
- **Never run `jiraworklog.exe --post-install`** (any build) on this
  machine: it rewrites the live Run key and copies the live DB. Only the
  installer, inside a sandbox, passes that flag.
